# 07. 세법 원문 수집·추출 파이프라인 (Law Ingestion)

## 목표

정부가 세법 개정을 발표·공포하면, **원본 문서를 자동으로 수집·보관(archive)** 하고, 그로부터 규칙 데이터([[03-rule-engine]])를 **추출·초안화 → 사람 검증 → 배포**하는 파이프라인을 갖춘다.

원칙:

1. **원문이 진실의 원천**: 모든 Rule은 보관된 원문 문서의 특정 조문을 가리켜야 한다. 블로그·뉴스 요약을 근거로 규칙을 만들지 않는다.
2. **원본은 불변 보관**: 수집 시점의 원문을 해시와 함께 저장한다. 나중에 "이 규칙을 만들 때 본 원문이 무엇이었나"를 재현할 수 있어야 한다.
3. **추출은 반자동, 승인은 사람**: 법령 텍스트 → 구조화 규칙 변환은 완전 자동화가 불가능하다(해석이 필요). LLM 보조 초안 + 필수 휴먼 리뷰로 설계하고, 리뷰 전 규칙은 `confidence: "drafted"`로 배포조차 하지 않거나 명시 표기한다.
4. **정적 호스팅과 분리**: 수집·추출은 GitHub Actions(저장소 측)에서 실행된다. 클라이언트는 결과물(규칙 JSON + 원문 링크)만 소비한다.

> 참고: 대한민국 법령·고시·판례는 저작권법 제7조에 따라 보호받지 못하는 저작물(공공 저작물)이므로 원문 보관·재배포에 저작권 문제가 없다. 보도자료는 공공누리 유형 확인 후 보관.

## 수집 대상 소스 레지스트리

| 소스 | 내용 | 형식 | 접근 방법 | 갱신 주기 |
|---|---|---|---|---|
| **국가법령정보센터 (law.go.kr) Open API** | 법률·시행령·시행규칙 전문. **시행일자별 연혁 조회 가능** — 우리의 bi-temporal 모델과 정합 | XML/JSON | 공개 Open API (신청 후 키 발급) | 일 1회 폴링 |
| 소관 법령 목록 | 소득세법, 소득세법 시행령·시행규칙, 지방세법(취득세·재산세), 종합부동산세법, 조세특례제한법(ISA·감면), 농어촌특별세법, 지방세특례제한법 | | 법령ID 고정 목록으로 관리 | |
| **국회 의안정보시스템 API** | 계류 중 개정안 (scheduled RuleSet의 원천) | XML/JSON | 열린국회정보 Open API | 주 1회 |
| **기획재정부 보도자료** | 세법개정안 발표(7월), 시행령 개정안(1월) — 개정 **의도와 요약표**가 담겨 있어 추출 가이드로 유용 | HWP/HWPX/PDF | RSS/웹 목록 크롤링 | 일 1회 |
| **행정안전부 보도자료** | 지방세(취득세) 개정 | HWP/PDF | 웹 목록 크롤링 | 주 1회 |
| **국토교통부 고시** | **조정대상지역·투기과열지구 지정/해제** — reference 규칙(지역×기간 테이블)의 원천 | 관보/고시문 | 관보 API 또는 국토부 고시 목록 | 주 1회 |
| 국세청 (후순위) | 기본통칙·예규·사례집 — 규칙 테스트 케이스의 원천 | HTML/PDF | 크롤링 | 수동 트리거 |

소스 레지스트리는 `pipeline/sources.json`으로 선언한다 (URL, 파서 유형, 폴링 주기, 담당 법령ID).

## 파이프라인 구조

```
┌────────────────── GitHub Actions (scheduled cron) ──────────────────┐
│                                                                      │
│ 1. WATCH   sources.json의 각 소스 폴링                                │
│            law.go.kr: 법령별 최종 개정일/시행일 비교                    │
│            보도자료/고시: 목록 페이지의 신규 항목 감지                   │
│                     │ 변경 감지                                       │
│ 2. FETCH   원문 다운로드 → law-archive/ 저장                          │
│            {sourceId}/{date}/{docId}.{xml|hwpx|pdf}                   │
│            + meta.json (URL, 수집일시, SHA-256, 시행일, 공포번호)       │
│                     │                                                 │
│ 3. PARSE   형식별 파서로 정규화 텍스트/구조 추출                        │
│            XML(법령) → 조문 트리(조/항/호/목, 시행일, 부칙)              │
│            HWPX → zip+XML 파싱 / PDF → 텍스트 추출                     │
│                     │                                                 │
│ 4. DIFF    직전 보관본과 조문 단위 diff                                │
│            → "소득세법 시행령 §154① 변경, 부칙 경과규정 신설"            │
│                     │                                                 │
│ 5. DRAFT   변경 조문 + 기존 규칙 매핑표 → LLM 보조 규칙 초안 생성        │
│            (Rule JSON 초안 + 근거 조문 인용 + 자동 테스트 스텁)          │
│                     │                                                 │
│ 6. PR      "규칙 갱신 PR" 자동 생성:                                   │
│            원문 diff + 규칙 초안(confidence: drafted) + 체크리스트       │
│                     │                                                 │
│ 7. REVIEW  사람이 원문 대조 검증 → confidence: verified로 승격,          │
│            테스트 케이스 보강 → 머지                                    │
│                     │                                                 │
│ 8. CI/CD   스키마 검증 + 규칙 테스트 + 회귀 스위트 → Pages 배포          │
│            → 클라이언트가 새 RuleSet 감지 → 개정 영향 리포트              │
└──────────────────────────────────────────────────────────────────────┘
```

단계 1~6은 자동, 7은 필수 수동 게이트다. **사람 승인 없이 규칙이 사용자에게 배포되는 경로는 존재하지 않는다.**

## 원문 보관소 (law-archive)

- 별도 저장소 `taxnavi-law-archive`로 분리 (원문 누적으로 메인 저장소 비대화 방지; HWP/PDF는 Git LFS).
- 디렉토리 구조:

```
law-archive/
  statutes/                       # law.go.kr XML
    soduksebeop/                  # 법령 단위
      2026-01-01_시행_제XXXXX호/
        law.xml                   # 원문 그대로
        parsed.json               # 조문 트리 (파서 출력)
        meta.json                 # url, fetchedAt, sha256, 공포일, 시행일
  notices/                        # 고시 (조정대상지역 등)
  press/                          # 보도자료
  bills/                          # 계류 의안
```

- `meta.json`의 SHA-256은 Rule의 `source` 필드에서 참조 → **규칙 → 원문 무결성 체인** 완성.

## Rule 스키마의 source 필드 확장

[[03-rule-engine]]의 `source`를 다음으로 강화한다:

```jsonc
"source": {
  "docId": "statutes/soduksebeop/2026-01-01_시행_제XXXXX호",  // law-archive 내 경로
  "sha256": "ab3f...",
  "articlePath": "제89조/제1항/제3호",     // 조문 트리 내 위치
  "quotedText": "…원문 인용(발췌)…",       // 리뷰·UI 표시용
  "url": "https://law.go.kr/...",          // 사용자용 외부 링크
  "checkedAt": "2026-07-15"
}
```

UI의 "왜 이 금액인가" 화면에서 quotedText와 law.go.kr 링크를 노출한다. 원문 전체를 클라이언트에 내려보내지는 않는다 (발췌 + 링크만).

## 추출(DRAFT) 단계 상세 — 반자동 설계

법령 조문 → Rule JSON 변환은 해석 행위이므로 다음처럼 좁게 설계한다:

1. **매핑표 (rule-mapping.json)**: 기존 각 Rule이 어떤 법령·조문에 근거하는지의 역인덱스. diff에서 변경된 조문이 감지되면 영향받는 Rule 목록이 자동 산출된다 → "이 개정으로 검토해야 할 규칙 7건".
2. **유형별 추출기**:
   - **파라미터형** (세율 수치, 한도 금액, 기간): 조문에서 숫자·기간 패턴 추출은 자동화 정확도가 높다. 기존 규칙과 값만 다르면 새 버전 초안 자동 생성.
   - **테이블형** (누진세율표, 장특공제표): 표 구조 추출 + 사람 검증.
   - **요건/판정형** (비과세 요건, 특례): 자동화 불가. LLM이 초안 + 원문 인용을 만들고 사람이 전면 재검토.
   - **부칙/경과규정**: 가장 위험한 부분. 부칙은 항상 사람이 직접 읽고 applicability 예외를 작성한다. 파이프라인은 "부칙 변경 감지 시 PR에 경고 라벨"만 자동화.
3. **LLM 사용 시 가드레일**: 프롬프트에 원문 조문만 입력(요약 기사 금지), 출력은 Rule JSON Schema로 강제, 초안에는 반드시 `confidence: "drafted"` + 원문 인용 포함, 인용이 원문과 문자열 일치하는지 CI가 기계 검증.

## 실패 모드와 대응

| 실패 모드 | 대응 |
|---|---|
| 소스 사이트 구조 변경으로 크롤러 파손 | WATCH 단계 실패 시 GitHub Issue 자동 생성. "마지막 성공 수집일"을 규칙 대시보드에 노출 — 조용한 실패 금지 |
| Open API 키 만료/쿼터 | Actions secret 관리, 실패 알림 |
| HWP 파싱 실패 | PDF 대체본 수집, 최후엔 수동 업로드 경로 (`pipeline/manual-drop/`) |
| LLM 초안의 그럴듯한 오류 | drafted 상태로 격리 + 인용 문자열 기계 검증 + 필수 리뷰 게이트 + 규칙 테스트 |
| 원문은 갱신됐지만 리뷰 지연 | 클라이언트에 "검토 중인 개정이 N건 있음" 배지 — 계산이 낡았을 수 있음을 사용자에게 고지 |

## 로드맵 반영

- **Phase 0**: law.go.kr Open API 키 발급 + 소득세법 시행령 1개 법령의 XML 수집·조문 트리 파싱 스파이크 (파서 실현성 검증). 수직 슬라이스의 규칙 2건에 source 필드(원문 해시·조문 경로)를 실제로 채워본다.
- **Phase 1**: WATCH+FETCH+ARCHIVE 자동화 (소관 법령 전체, 일 1회 cron). diff는 조문 텍스트 단위. PR 자동 생성은 원문 diff 첨부까지 (규칙 초안은 수동).
- **Phase 2**: 조문→규칙 매핑표 구축, 파라미터형 자동 초안, 부칙 경고 라벨, 조정대상지역 고시 수집.
- **Phase 3**: LLM 보조 초안(요건형), 의안 API 연동(scheduled RuleSet), 국세청 사례집 → 테스트 케이스 반자동화.
